# Aqua360 Customers

Web application for billing and managing water subscribers. This repository contains all the code needed to install and run it (API, background tasks, user interface, and support services).

## Requirements

- [Docker](https://docs.docker.com/get-docker/) and Docker Compose (included with Docker Desktop).

## Quick Start: Run with Docker

### 1. Project Directory

```bash
cd /path/al/projecte/aqua360-customers
```

### 2. Environment Variables (`.env`)

`docker-compose.yml` loads the `.env` file (`env_file`) in the `backend`, `celery-worker`, `celery-beat`, `gmao-consumer` and `frontend` services, so it **must exist** at the project root:

```bash
cp env.docker.example .env
```

Edit `.env` if needed. For example, if port **5432** is already used by a system PostgreSQL instance, set `POSTGRES_PORT=5433` (only the port on the host machine).

Any variable in `.env` (e.g. `EMAIL_*`, `MSGRAPH_*`, `DOMAIN_MEDIA`, `CSRF_TRUSTED_ORIGINS`) reaches the containers. The DB and Redis connection variables (`DATABASE_*`, `CELERY_BROKER_URL`) are set by the compose file itself, and the rest have defaults in `docker-compose.yml`. `ENV` and `LANGUAGE` apply to the frontend build and runtime.

### 3. Build and Start All Services

The first time, or after changes to Dockerfiles or dependencies:

```bash
docker compose up --build
```

The first build may take a while (base images, `pip`, `npm run build`).

To run in the background:

```bash
docker compose up --build -d
docker compose logs -f
```

### 3.b If Only `.env` Has Changed

You do not need to rebuild images if you have not changed Dockerfiles or dependencies.

```bash
docker compose up -d --force-recreate
```

This recreates the containers so they pick up the new environment variable values.

If you changed `NUXT_PUBLIC_API_HOST` (a variable used when building the frontend), then a rebuild is required:

```bash
docker compose up -d --build frontend
```

### 4. Container Status

```bash
docker compose ps
```

All services should be running (and `healthy` where applicable). All of them use `restart: unless-stopped`, except `gmao-consumer` (`on-failure`: it exits cleanly when RabbitMQ is disabled).

| Service | Purpose |
|---|---|
| `db` | PostgreSQL 16 |
| `redis` | Celery broker |
| `backend` | Django API |
| `celery-worker` | Background tasks |
| `celery-beat` | Scheduled tasks |
| `gmao-consumer` | GMAO consumer (`manage.py run_gmao_consumer`) |
| `frontend` | Nuxt interface |

### 5. Administration and Test Data

With the services running, open another terminal. From the project root, you do not need to `cd` into the backend if you use `exec` as shown below.

**Demo environment with Prometeo** - the `backend/prometeo/reset_db.sh` script regenerates a test world (exploitations, contracts, readings, etc.):

```bash
docker compose exec backend bash prometeo/reset_db.sh
```

This runs `flush` on the database: it **deletes all data** and reloads the dataset generated by Prometeo. It also creates a superuser and token through the `create_superuser_and_token` management command (see the script itself if you want to change credentials).

**Only a superuser** (without clearing or regenerating the world):

```bash
docker compose exec backend python manage.py createsuperuser
```

To run the same script without Docker, you must be inside `backend/` with the Python environment active; see the comments at the top of `prometeo/reset_db.sh`.

### 6. URLs

| What to Open | URL |
|--------------|-----|
| User interface | http://localhost:3000 |
| Admin panel | http://localhost:8000/admin/ |

The web interface uses the API URL defined by `NUXT_PUBLIC_API_HOST` (default: `http://localhost:8000`). If you change it, you must **rebuild** the corresponding Compose image.

### 7. Stop

```bash
docker compose down
```

PostgreSQL data is stored in the Docker volume and is preserved between runs. To also remove the volumes:

```bash
docker compose down -v
```

## Production Deployment (Summary)

### Recommended Flow

```bash
git pull
docker compose build frontend backend celery-worker celery-beat gmao-consumer
docker compose up -d backend
docker compose exec backend python manage.py migrate --noinput
docker compose up -d celery-worker celery-beat gmao-consumer
docker compose up -d frontend
```

### Automated Deployment (Ansible)

Servers are deployed with the `playbooks/AquaCustomersDocker` playbook of the `aqua360-customers-deploy` repository (`99-all.yaml` runs them all in order, using the client inventory):

| Playbook | What it does |
|---|---|
| `00-users-workdir` | Users and the `/var/www/<exploitation>` working directory |
| `01-compose-env` | Copies `docker-compose.yml`, generates `.env` from the inventory and creates `backups/`, `docker-data/`, `backend/` and `frontend/` |
| `02-git-clone` | Clones the code and runs `docker compose up --build -d` |
| `03-nginx-docker-cloudflare` | Cloudflare Origin certificates and Nginx sites proxying to the Docker ports |
| `04-backup-db` | `backup_db.sh` (`pg_dump` inside the `db` container) and backup cron |
| `05-copy-backup-to-test` | Daily copy of the latest backup to the test server |
| `06-restore` | `restore.sh` and cleanup of old databases (3-day retention) |
| `07-readonly-db-user` | Read-only PostgreSQL user |

On servers the host ports are not the defaults (`POSTGRES_PORT=5433`, `REDIS_PORT=6380`, `BACKEND_PORT=8001`, `FRONTEND_PORT=3001`) and can be changed per client in the inventory (`docker_*_port`) so several exploitations can share a server. The `docker-compose.yml` in this repository is the same one the playbook deploys.

### Service Interruption: What to Expect

- `docker compose build ...` does **not** interrupt service: it only builds images.
- `docker compose up -d ...` may cause a **brief interruption** when recreating containers (on a single host with a single replica per service).
- During `up`, the old service may continue running briefly, but there may be a few seconds of unavailability at replacement time.
- If near-zero downtime is required, use blue/green or rolling updates with a reverse proxy/orchestrator.
